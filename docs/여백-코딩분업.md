# 여백 — 코딩 분업 (GitHub 협업)

> 영상·설명서 등 코딩 외 작업은 제외. 기준 문서는 `여백-기획서최종.md`.
> ⚠ 이 문서는 1단계(화면)가 끝난 뒤 다시 정리한다. 용어는 `여백-네이밍규칙.md`가 우선한다 (예: 전문가 해석 클래스는 `ExpertInterpretation`).

## 1. 역할

| | 담당 | 화면 | 맡는 코드 |
| --- | --- | --- | --- |
| **A** | 에이전트 · 대화 | S05 | OpenRouter 클라이언트, 에이전트 루프(툴 4개 연결), 툴 `verify_quote` · `search_poem_lines`, 출력 필터, 대화 화면, **테마 · 공용 위젯** |
| **B** | 읽기 흐름 | S03 S04 S06 | 홈, 읽기, 정리·저장, **시 본문 위젯(공용)**, 누적일수 |
| **C** | 계정 · 설정 · 데이터 | S01 S02 S10 S11 | 로그인·가입, 무작위 닉네임, 설정, **모델·저장소(공용)**, **라우터·pubspec**, Firestore 규칙 |
| **D** | 대조 · 커뮤니티 · 프로필 | S07 S08 S09 S12 | 툴 `compare_with_experts` · `get_poem_context`, 전문가 해석 파서, 커뮤니티, 공감, 프로필, 뱃지 |

- **A가 가장 어렵다.** 막히면 과제가 성립하지 않으므로 가장 손 빠른 사람이 맡는다.
- **공용 코드는 주인이 한 명씩 있다.** 테마·공용 위젯·OpenRouter 클라이언트는 A, 시 본문 위젯은 B, 모델·저장소·라우터는 C. 다른 사람은 고쳐 달라고 요청하거나 작은 PR로 제안한다.
- **화면부터 만든다.** 1단계 화면 분업은 `여백-화면분업.md`. 이 문서는 2단계(기능) 기준이다.

## 3. 1주차에 같이 정할 것 — 계약

이게 안 정해지면 나머지가 서로 기다린다. **코드보다 먼저 이름과 모양을 합의**한다.

### 데이터 모델 (C가 초안, 전원 합의)

| 모델 | 들어가는 것 |
| --- | --- |
| `Poem` | id, 제목, 작가, 연도, 행 목록, 뱃지 이미지 경로 |
| `ExpertInterpretation` | 라벨(A/B), 입장, 주장 목록(근거 행 번호 + 핵심 문장) |
| `Reading` | 시 id, 첫 낱말, 멈춘 행, 대화 기록, 해석, **근거 행 번호 목록**, 저장 여부, 대조 열람 여부 |
| `PublicConversation` | 작성자 uid, 시 id, 첫 낱말, 요약, 최종 해석, 공감 수 |
| `UserProfile` | 닉네임, 누적일수, 마지막으로 센 날짜, 받은 뱃지 목록 |
| `Settings` | 질문 모델, 비교 모델, 말투 |

### 경계 세 곳

| 주는 쪽 → 받는 쪽 | 무엇을 | 합의할 내용 |
| --- | --- | --- |
| **A → B, D** | 대화에서 확인된 근거 행 | 행 번호 목록 형식, `Reading`에 언제 쓰는지 |
| **A → D** | OpenRouter 클라이언트 | 모델 이름 넘기는 방법, 실패 시 무엇을 돌려주는지 |
| **B → D** | 저장 완료 | 저장 시 뱃지 지급과 공개 대화 생성을 누가 호출하는지 |
| **D → A** | 툴 두 개 | `compare_with_experts` · `get_poem_context`의 입력·반환 형식. A의 루프가 이 둘을 부른다 |

### 가짜 저장소

C는 1주차에 **가짜 저장소(fakes)** 를 먼저 만든다. 메모리에 데이터를 들고 있는 버전이다. Firestore가 연결되기 전에도 B·D가 화면을 끝까지 만들 수 있다. 진짜로 바꿀 땐 한 곳만 갈아끼운다.

A도 같은 방식으로 **고정 응답을 돌려주는 가짜 에이전트**를 먼저 내놓는다. B는 이걸로 S05 → S06 흐름을 붙여볼 수 있다.

## 4. 브랜치 전략

```
main      ← 제출·시연용. 직접 push 금지
  └─ develop   ← 통합. 매주 수업일에 main으로
        ├─ feat/chat-verify-quote      (A)
        ├─ feat/reading-poem-view      (B)
        ├─ feat/auth-random-nickname   (C)
        └─ feat/compare-relation       (D)
```

| 규칙 | 내용 |
| --- | --- |
| 브랜치 이름 | `feat/<영역>-<설명>`, 버그는 `fix/…` |
| PR 대상 | 항상 `develop` |
| 리뷰 | **1명 이상 승인**해야 병합. 자기 영역 밖을 건드렸으면 그 주인이 리뷰 |
| 병합 | Squash merge (한 기능 = 커밋 하나) |
| PR 크기 | 화면 하나, 기능 하나 단위. 크면 쪼갠다 |
| `main` 병합 | 매주 수요일 수업 시간에, 앱이 빌드되는 걸 확인하고 |
| 보호 | `main`·`develop` 모두 브랜치 보호 켜기 |

### 충돌이 잘 나는 파일

| 파일 | 주인 | 규칙 |
| --- | --- | --- |
| `pubspec.yaml` | C | 패키지 추가는 **그것만 담은 작은 PR**로. 다른 작업과 섞지 않는다 |
| `router.dart` | C | 화면 추가 시 경로 한 줄만 넣는 PR |
| `theme.dart` | A | 색·글꼴은 여기서만. 화면에 색 코드를 직접 쓰지 않는다 |
| `strings.dart` | 전원 | 자기 화면 문구만 추가. 남의 줄은 고치지 않는다 |
| `main.dart` | C | 거의 안 건드림 |

### 비밀값

- OpenRouter 키는 `--dart-define`으로 넣고 코드·저장소에 **절대 쓰지 않는다**
- Firebase 설정 파일(`google-services.json`)도 `.gitignore`에 넣고 팀 채팅으로만 공유
- 실수로 올렸으면 커밋을 지워도 이미 늦다. **교수님께 키 재발급을 바로 요청**

## 5. 순서

| 단계 | A | B | C | D |
| --- | --- | --- | --- | --- |
| **1 · 기반** | 테마, 공용 위젯, 가짜 에이전트 | 시 본문 위젯 | 프로젝트 셋업, 모델, 가짜 저장소, 라우터 | 가짜 데이터, 전문가 해석 JSON 형식, 파서 |
| **2 · 단독 개발** | **에이전트 PoC** (서시 한 편, verify_quote, 재탐색) | S03 · S04 | S01 · S02, Firebase Auth | 관계 계산 로직 (가짜 데이터로) |
| **3 · 화면 완성** | S05, 출력 필터 | S06, 누적일수 | S10 · S11, Firestore 연결 | S07 · S12 |
| **4 · 연결** | 진짜 에이전트로 교체 | 가짜 → 진짜 저장소 | 보안 규칙 | S08 · S09, 비교 문장·요약 |
| **5 · 통합** | 전원 — 시연 시나리오대로 끝까지 돌려보고 버그 수정 ||||

### 확인 지점

- **2단계 끝 — 에이전트 PoC.** 무료 모델에서 툴 호출이 되는지 여기서 결판낸다. 안 되면 **D가 A를 돕고 커뮤니티(S08·S09)를 뒤로 미룬다.** 커뮤니티는 빠져도 요건을 만족하지만 에이전트는 빠지면 과제가 성립하지 않는다.
- **3단계 끝 — 가짜 데이터로 처음부터 끝까지.** 로그인 → 읽기 → 대화 → 저장 → 대조가 가짜 저장소 위에서라도 한 번 이어져야 한다.
